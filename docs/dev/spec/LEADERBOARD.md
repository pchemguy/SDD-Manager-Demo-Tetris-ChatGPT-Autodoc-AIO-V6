# Leaderboard and portable files

## L-01: Result and session contracts

A result has exactly `id`, `score`, `timestamp`. IDs are stable case-sensitive ASCII strings of length 1–64 matching `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`; newly completed games use unique UUID strings generated by browser crypto or an injected equivalent. Do not regenerate IDs when sorting, exporting or restoring. Score is an integer in `0..9007199254740991`; reject numeric strings, null, NaN, fractions and out-of-range values.

Timestamp is canonical UTC `YYYY-MM-DDTHH:mm:ss.sssZ`, years 0001–9999, with a real Gregorian calendar date and valid hour/minute/second/millisecond. Reject impossible dates, offsets, missing Z, omitted milliseconds, leap seconds and year zero. Use exact canonical round-trip/calendar validation, not a permissive date parse alone. The public schema's `utc-timestamp` format requires this predicate.

Keep the collection in page memory only. Reload/navigation discards it; restart does not. Insert once for each game-over event, including a zero score; do not record abandoned games. Sort by descending score, then ascending timestamp, then ascending ID by ASCII code-point order. Retain the first ten; equal scores remain separate results. IDs must be unique. A fresh game after restore creates an ID absent from restored records. Display rank, score and completion time with an explicitly identified timezone.

## L-02: JSON contract

JSON root is `{ "formatVersion": 1, "results": [...] }`, with zero to ten results. The bundled [JSON Schema](LEADERBOARD-SCHEMA.json) is the structural contract; publish a downloadable copy with the application. Reject unknown properties, missing fields, wrong types and unsupported versions. Validate against that schema with strict `utc-timestamp` format enabled, without type coercion, inserted defaults or removal of properties. Then validate semantic ID uniqueness and shared result invariants before replacement. Merely checking the format field is insufficient.

Export UTF-8 JSON with the ranked current results and `.json` filename. Restore accepts unsorted valid input and applies the canonical rank; preserve each record's values exactly. Read at most 65536 bytes; reject larger JSON before decoding. Malformed UTF-8 or JSON is an error. Standard JSON parsing applies; duplicate IDs in the results array are always an error.

## L-03: SQLite contract

Export a genuine SQLite 3 database, identified by its standard header bytes, with `PRAGMA user_version=1`. It has one ordinary application table:

```sql
CREATE TABLE high_scores (
    id TEXT NOT NULL PRIMARY KEY,
    score INTEGER NOT NULL CHECK (score >= 0 AND score <= 9007199254740991),
    timestamp TEXT NOT NULL
);
```

Populate with bound parameters; use no additional application table for version metadata. An automatically created primary-key index is permitted. Export zero to ten ranked results. SQL row order is not a ranking guarantee; restore applies the shared ranking function.

Read at most 1048576 bytes before database initialization. Import in a disposable worker/database. Require user_version exactly 1, integrity_check returning exactly `ok`, one ordinary `high_scores` table and the three columns in the stated order with matching declared types, NOT NULL flags and `id` primary-key position. Inspect all columns, including hidden/generated flags; reject hidden/generated columns, virtual tables, extra application tables, triggers, views and extra user-created indexes. SQLite internal primary-key index metadata is allowed; do not demand byte-for-byte DDL text equality or depend on whitespace. No imported DDL or SQL text is executed by the application. Enable supported query-only/untrusted-schema protections before inspecting application rows.

Read up to eleven rows to detect excess results; an eleventh row rejects the database. Check actual row value types, not only column declarations: score must have SQLite integer storage class and remain a JavaScript safe integer; ID/timestamp must have text storage class. Run shared record/timestamp/uniqueness validation on every decoded row. CHECK constraints alone are not acceptance evidence; malicious or externally constructed files may bypass them. Unknown versions, invalid schema, corruption, encrypted/non-SQLite input and runtime initialization failure are visible errors.

## L-04: File UI and atomicity

Place Save and Restore below the leaderboard. Save offers JSON or SQLite, downloads a snapshot and never clears results. Empty exports are valid. Restore opens a picker accepting either format, detects content rather than trusting extension/MIME, and replaces rather than merges results. Recognize SQLite by its header; otherwise attempt bounded UTF-8 JSON and reject unsupported content clearly. An extension mismatch may succeed when the content is a valid supported format.

File dialogs/cancellation do not change results. Pause gameplay while Save/Restore is active; disable overlapping file operations and restart. On success show a concise result/count status. On failure show a clear error category/message, re-enable controls, release resources and keep the previous collection byte-for-byte equivalent in value and order. Do not ask for overwrite confirmation: Restore's documented purpose is replacement.

Bound codec work by a 10000 ms whole-operation deadline after file bytes are available, including SQLite initialization/worker processing. Terminate the owned worker on timeout; ignore late replies. File selection itself has no deadline. Save/Restore completion removes only the file-operation pause reason. Release all temporary database/statements, file buffers, listeners and workers; revoke download object URLs after consumption/failure. An unavailable SQLite runtime disables only the affected operation with a clear error; gameplay, session scores and JSON remain functional.

Acceptance uses genuine JSON/SQLite empty/full round trips, preserved IDs/scores/times, ties/truncation, valid unsorted import, wrong-type/extra-field/schema/version/UTF-8/date/count/size/corruption failures, cancel/timeout/stale-reply behavior, resource teardown and unchanged prior state. Browser tests exercise actual file upload and download bytes in both required browsers.
